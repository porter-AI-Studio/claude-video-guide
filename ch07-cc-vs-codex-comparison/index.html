第 7 章 · Part 3：實戰操作

雙工具對照與選型建議

前兩章分別示範了「CC 直接下 /watch」與「CC 用 codex exec 操控 Codex 執行 /watch」。這兩條路徑都能讓 AI 看懂影片，但適合的情境不同——這一章把它們並排比較，幫你決定該選哪一條。

兩條路徑，同一個 skill

claude-video 是同一份 skill，只是安裝的落點與呼叫方式因 harness 而異：

面向CC 直接用CC 操控 Codex
安裝方式Plugin marketplace（/plugin install watch@claude-video）Skills registry（npx skills add ... -g -a codex）
安裝落點~/.claude/plugins/cache/claude-video/watch/<版本>/skills/watch/~/.agents/skills/watch/
呼叫方式對話框直接打 /watch <url>Bash 呼叫 codex exec 非互動模式
互動性互動式，可追問、可調整非互動，一次 prompt 收斂一次結果
權限把關Claude Code 自己的分類器Claude Code 分類器 + Codex 沙盒，雙重關卡
結果留痕留在 CC 對話記錄留在 CC 對話記錄，且可額外用 -o FILE 落地成檔案
適合場景單次、探索性的「看一支影片問問題」可程式化、可重複執行的批次任務／pipeline 一環
ℹ️
安裝位置不同，但金鑰設定只需要做一次

雖然兩條路徑的安裝目錄不同，claude-video 讀寫的執行期設定檔卻是同一份、固定路徑的 ~/.config/watch/.env——跟你透過哪個 harness 呼叫無關。也就是說金鑰只要設定一次，兩條路徑都能直接用；反過來說，如果哪天真的同時、併發地跑兩條路徑，也要留意這份共用檔案可能被交錯寫入覆蓋（第 6 章「多 Claude Code session 併行時的隔離規則」已有實測記錄）。

什麼時候該選哪一條？

選「CC 直接用」，如果……

  • 你只是想看一支影片、問幾個問題，互動性優先
  • 不需要把這個動作嵌進更大的自動化流程
  • 想要邊看邊追問細節（例如追問「第 30 秒那個手勢是什麼意思」）

選「CC 操控 Codex」，如果……

  • 要處理的是一批影片，需要固定格式、可重複執行的腳本化流程
  • 想把「看影片」這一步當成更大 pipeline 的一環（例如：CC 前處理找 video id → Codex 執行 /watch → CC 後處理寫進 Obsidian 筆記）
  • 需要驗證同一個 skill 在多個 harness 都可用，例如評估要不要讓團隊統一遷移到某個 harness
💡
兩者不是二選一，可以並用

實務上更常見的模式是：探索階段用「CC 直接用」快速摸清一支影片在講什麼；確認流程可行後，把重複性高的部分改寫成「CC 操控 Codex」的腳本化任務，讓它可以無人值守地批次執行。

探索用「CC 直接用」，自動化用「CC 操控 Codex」——兩條路徑不是二選一，是分工。

共通的心法：最小權限

不管走哪一條路徑，這本書反覆出現的一條原則是——最小權限的指令同時更安全、也更容易被 Claude Code 的權限分類器放行。與其反射性地要求最高權限（danger-full-access、--dangerously-bypass-approvals-and-sandbox），不如先問清楚「這個子任務到底缺哪一項能力」，再精準補上——上一章 -c 'sandbox_workspace_write.network_access=true' 就是最好的例子：只補了「連網路」這一項，其餘限制照舊維持。

小結

claude-video 展現的不只是「AI 能看影片」這一件事本身，更示範了同一個 Agent Skill 如何在不同 harness 之間無縫遷移、甚至被另一個 AI 當成可程式化的執行單元來調度。下一章我們回到更務實的問題：怎麼控制成本，不同 --detail 模式的取捨到底差在哪裡。
