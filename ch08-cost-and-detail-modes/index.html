第 8 章 · Part 4：進階與案例

成本控制與 detail 模式

transcript / efficient / balanced / token-burner，四選一背後的成本邏輯。

成本模型：只有一件事真正燒錢

claude-video 的成本結構其實很直覺：有原生字幕的影片，全程幾乎免費——yt-dlp 抓字幕不用錢，交給 Claude 分析文字的 token 成本相對很低。真正燒錢的是畫面影格：每一張送進 Claude 的圖片都要吃掉一筆視覺 token，這才是預算失控的主要來源。

換句話說，決定成本的關鍵問題不是「這支影片長不長」，而是「這次任務需不需要看畫面」。如果只要文字內容（例如聽一場演講的重點），選擇不抽圖的模式就是最省的做法。

四種 detail 模式

模式抽圖策略適用情境
transcript完全不抽圖，純逐字稿只要文字內容、成本最低
efficient場景感知去重，上限 50 張需要少量畫面佐證
balanced（預設）場景感知去重，上限 100 張一般用途的最佳平衡
token-burner場景感知去重，不設上限需要盡可能完整的畫面覆蓋（成本高，謹慎使用）
四種模式的實際下法
/watch <URL> --detail transcript   # 純文字，最省
/watch <URL> --detail efficient    # 少量畫面佐證
/watch <URL> --detail balanced     # 預設，一般用途
/watch <URL> --detail token-burner # 影格無上限，成本最高
💡
選擇原則：先問「這個任務需不需要看畫面」

螢幕錄影除錯、UI 走查、影片開場拆解——這類任務畫面本身就是資訊，該用 balanced 甚至 token-burner。演講摘要、會議記錄、單純想知道「這支影片在講什麼」——文字就夠了，transcript 永遠是第一選擇，不要反射性地用預設值。

ℹ️
量級概念：差距有多大？

不需要精算到小數點，抓一個量級概念就夠：transcript 模式對一支 20 分鐘影片，成本主要是幾千字逐字稿的文字 token，相對便宜；balanced 模式若真的用滿 100 張影格，等於額外多送進去 100 張圖片，每張圖片的視覺 token 消耗通常是同等長度文字的數倍到十幾倍——兩者疊加起來，一次呼叫的成本很容易差到一個數量級以上。實際數字會隨模型定價與影格解析度變動，重點是建立「文字便宜、畫面貴很多」這個相對感，選模式時心裡有個尺。

為什麼去重演算法很重要

即使選了會抽圖的模式，claude-video 也不會暴力擷取每一影格。它內建一套去重演算法：把每張畫面縮成 16×16 的迷你灰階圖，只保留跟「前一張被選中的畫面」差異夠大的影格——可以想成一位很嚴格的剪接師，把靜止或緩慢變化的冗餘畫面全部剪掉。這代表就算選 balanced 或 token-burner，實際送進 Claude 的影格數量也遠比「每秒截一張圖」少很多，是這套架構把成本壓低的核心設計（第 2 章有完整架構拆解）。

Whisper 轉錄的額外成本

成本模型還有一個變數：影片本身有沒有字幕。有字幕就完全不會觸發 Whisper，這部分零成本；沒字幕才會啟動語音轉錄 fallback，這時才需要 Groq 或 OpenAI 的 API 額度。這也是為什麼建議優先填 GROQ_API_KEY（第 3、4 章已提過安裝時的設定）——比 OpenAI 便宜也快，能在轉錄這一步就控制住成本。

⚠️
金鑰安全性是額外要考慮的成本

claude-video 引導使用者把 API key 明文存放在 ~/.config/watch/.env，相較作業系統內建的金鑰管理服務安全性偏低。個人使用問題不大，但若要在共用機器或企業環境部署，這點需要另外評估金鑰輪替與存取控管。

實務建議：先用 transcript 探路

不確定一支影片值不值得花畫面 token 分析時，先用 transcript 模式跑一次，看文字摘要是否已經回答了你的問題。真的需要畫面佐證（例如「這個 bug 出現在哪個畫面」），再針對那個時間區段重新用 efficient 或 balanced 跑一次——比一開始就無腦選 token-burner 省下大量不必要的成本。

小結

claude-video 的成本控制邏輯，說到底就是一句話。

文字幾乎免費，畫面才要錢，去重演算法負責把畫面成本壓到最低。
