第 6 章 · Part 3：實戰操作

Codex 實務：codex exec 呼叫 claude-video

claude-video 不是 Claude Code 專屬工具，Codex 也能裝。這一章更進一步：讓 Claude Code 本身當「指揮官」，透過 codex exec 非互動模式，把 /watch 任務派給 Codex 執行——並記錄下這條路上踩到的兩個關卡。

為什麼要「cc 操控 codex」，而不是直接開 Codex 手打？

  • 留痕：整個過程（指令、輸出、清理）都留在 Claude Code 的對話記錄裡，可回溯、可直接寫進筆記庫。
  • 編排：Claude Code 可以先做前處理（找 video id、決定 --detail 模式），再把定義清楚的子任務丟給 Codex，收完結果接著做後處理，形成一條可重複的 pipeline。
  • 驗證雙環境：同一個 skill 在兩種 harness 都跑通，才算真正「跨 agent 可用」，而不是只在自己熟悉的環境裡測試過。

在 Codex 安裝 claude-video

跟 Claude Code 的 plugin marketplace 不同，Codex（以及 Cursor、Gemini CLI 等其他 harness）是透過 skills registry 安裝：

一般終端機（非 Claude Code 對話框）
# 全域安裝，裝給所有支援的 harness
npx skills add bradautomates/claude-video -g

# 只裝給 Codex
npx skills add bradautomates/claude-video -g -a codex
⚠️
這行指令要自己在終端跑，不能請 Claude Code 代勞

在 Claude Code 的 auto 權限模式下，npx skills add ... -g 這種「安裝全域套件」的指令會被權限分類器判定為高風險而直接擋下。正確做法是自己在一般終端機執行，Claude Code 這一側只負責事後確認 ~/.agents/skills/watch/SKILL.md 是否存在。

裝完後，skill 會落在 ~/.agents/skills/watch/（不是 ~/.codex/skills/——這個路徑在多數機器上根本不存在）。目錄結構：

skill 目錄結構
~/.agents/skills/watch/
├── .skillignore
├── SKILL.md
└── scripts/
    ├── watch.py         ← 主控
    ├── whisper.py       ← Groq/OpenAI 純 stdlib client
    ├── frames.py
    ├── download.py
    ├── transcribe.py
    ├── setup.py
    └── config.py

codex exec 速查

codex exec 是 Codex 的「非互動模式」，語法是 codex exec [OPTIONS] [PROMPT]。以下是這次實戰真正用到的旗標：

旗標作用
-c, --config key=value覆寫 ~/.codex/config.toml 設定值，支援 dotted path，value 以 TOML 解析——本次的關鍵旗標
-s, --sandbox MODE沙盒策略：read-only / workspace-write / danger-full-access
--skip-git-repo-check允許在非 git 目錄跑，本次每次都必帶
--ephemeral不把 session 檔寫到磁碟，驗證性質不需要留存
-o, --output-last-message FILE把 agent 最後一則訊息寫到檔案，是收結果最穩定的方式
ℹ️
approval policy 是 never

codex exec 預設 approval_policy=never——它不會停下來問你，要嘛在沙盒能力內做完，要嘛因權限不足直接失敗。所以「給多少權限」必須在啟動旗標就一次決定好，這也是接下來兩道關卡的根源。

兩道關卡

關卡 A：Claude Code 自己的權限分類器

在 auto 權限模式下，Claude Code 會用分類器判斷 Bash 指令風不風險。實測結果：

指令結果
npx skills add ... -g❌ 被分類器擋（安裝全域 skill 視為高風險）
codex exec -s danger-full-access ...❌ 被分類器擋
codex exec -s read-only ...✅ 放行
codex exec -c 'sandbox_workspace_write.network_access=true' ...✅ 放行

最後一行沒有另外加 -s：codex exec 不指定 -s 時，預設沙盒本來就是 workspace-write，所以只用 -c 補一項設定就夠了——這個預設值跟接下來「關卡 B」要處理的問題其實是同一件事。

關卡 B：Codex 自己的沙盒

沙盒（sandbox）是指限制一個程式能存取哪些檔案、能不能連網路的隔離機制——目的是就算裡面執行的指令出錯或帶有惡意，影響範圍也只侷限在沙盒劃定的邊界內，不會波及整台機器。Codex 執行任務時預設就在這樣的沙盒裡跑，workspace-write 沙盒預設只准寫工作區、且不開對外網路。而 /watch 需要 yt-dlp 連 YouTube 抓字幕（沒字幕還要連 Groq），純 workspace-write 會在下載那一步直接失敗。

💡
解法：只補缺的那一項能力

不要反射性地丟 danger-full-access。先問「這個子任務到底缺哪一項能力」——這次只缺「對外連 YouTube / Groq」，那就只補 network_access：

-c 'sandbox_workspace_write.network_access=true'

維持 workspace-write 的檔案系統限制，只把網路打開——這樣同時更安全、也更容易過 Claude Code 的分類器。

最小權限不是保守，是效率——每多開一項用不到的權限，就多一次被分類器擋下來的機會。

完整驗證指令

以下指令統一用 bash 語法（\ 續行、單引號字串）撰寫——因為這裡的情境是 Claude Code 透過自己內建的 Bash 工具把指令送給 Codex，跟前面幾章「使用者自己在 PowerShell 貼指令」是不同場景，續行符號不是 PowerShell 的反引號 `。若要在 PowerShell 手動照打，續行與引號規則都得換成 PowerShell 的寫法。

先唯讀探測，確認 Codex 端真的有這個 skill（絕不在探測步驟安裝或寫入）：

階段 1：能力探測
codex exec --skip-git-repo-check -s read-only --ephemeral -o probe.txt \
  "Do you have an agent skill named 'watch' (bradautomates/claude-video)? \
   Check ~/.codex/skills and ~/.agents/skills, list any video-related skill \
   with its SKILL.md path. Reply in <=4 lines. Do not install anything."

確認 skill 已就位後，用最小權限正式派任務。指令裡的 <scratchpad> 是佔位符，代表 Claude Code 為這個工作階段配置的暫存工作目錄（路徑通常帶有 session id）——實際執行時要換成當下工作階段真正的路徑：

階段 2：正式執行（最小權限）
cd "<scratchpad>" && codex exec --skip-git-repo-check \
  -c 'sandbox_workspace_write.network_access=true' --ephemeral \
  -o result.txt \
  "Use the 'watch' agent skill (script at ~/.agents/skills/watch/scripts/watch.py, \
   run with python on Windows). Fetch the transcript of \
   https://www.youtube.com/watch?v=oBuWXUy7stw with --detail transcript. \
   Then report: (1) title (2) duration (3) transcript source captions-vs-whisper \
   (4) segment count (5) 3-bullet summary. Under 14 lines. No frame extraction."

這次驗證的實際結果：

項目結果
影片Claude Code + Codex = AI GOD MODE!（18:14）
逐字稿來源captions（YouTube 自動字幕，非 Whisper）
段數493
結果pipeline 完整跑通：定位 skill → watch.py --detail transcript → yt-dlp 抓字幕 → 產出報告

Prompt 撰寫要點

非互動模式下你通常只有一次收斂機會，怎麼寫 prompt 直接決定成敗：

  1. 明確給出腳本絕對路徑與直譯器——~/.agents/skills/watch/scripts/watch.py、Windows 要註明 run with python（不是 python3），不要讓 Codex 自己猜路徑。
  2. 指定輸出格式與行數上限——「report exactly (1)…(5)…」「under 14 lines」，格式框死了才好解析結果。
  3. 一個 prompt 一個子任務，不要把「安裝 + 執行 + 整理」塞進同一個指令。

為什麼「Codex 說沒有」但機器其實有？

初次探測時，Codex 曾回報 python／ffmpeg／yt-dlp 都不存在，但實體機器上這些工具明明都裝好了。原因有三個：

  • 沙盒 PATH ≠ 實體機器 PATH——Codex 在受限沙盒跑指令時，看到的環境變數是被裁過的。
  • skill 探測有時序問題——探測當下 watch 可能還沒（或剛裝一半）出現在 ~/.agents/skills/，skill discovery 不是即時的。
  • 巢狀目錄雜訊——有些 skill 落在 ~/.agents/skills/skills/<name>/（雙層），有些在 ~/.agents/skills/<name>/（單層），列目錄判斷「有沒有裝」時兩層都要看。
⚠️
教訓

判斷「某工具/skill 在不在」要在目標 harness 拿到足夠權限後實測，不能只靠另一個 agent 在受限沙盒裡的回報下結論。

沙盒說「沒有」，不代表機器上真的沒有——它只代表沙盒不准你看到。

多 Claude Code session 併行時的隔離規則

如果你會同時開多個 Claude Code session、各自呼叫 Codex，要留意幾個跨 session 共用的資源：

路徑風險規則
各自的 scratchpad無（路徑自帶 session id）直接用，天生隔離
~/.config/watch/.env併發寫入互相覆蓋Edit 前務必重新 Read，不要假設快取仍是最新
共用輸出資料夾（如 _generated/）檔名衝突、誤讀別人的產出檔名/路徑一律帶呼叫端 session id 前 8 碼
Codex CLI 帳號 / CODEX_HOME併發時 session/thread 記錄互相干擾常態併發才需要各自配獨立 CODEX_HOME，非預設做法

另外一條規則同樣重要：如果任務未來需要接續（也就是這次刻意不加 --ephemeral，讓 session 檔留下來），不要用「resume 上一個」這種語意含糊的指令。多 session 併行時，「上一個」很容易對不到自己這條 thread；要接續任務，一定要用該次呼叫明確回傳的 agent id，沒有明確 id 就當成全新任務重開。本章前面的驗證指令全程都帶 --ephemeral，本來就不留 session 檔，自然也沒有「接續」的問題——這條規則是給需要留存、之後要接續的常態任務用的。

小結

這一章證明了兩件事：claude-video 本身能跨 harness 使用；而且「Claude Code 當指揮官、Codex 當執行單元」這條操作路徑是可行且可複用的——核心心法是最小權限、格式框死、留痕可回溯。下一章把 CC 直接用和 CC 操控 Codex 這兩條路徑並排比較，幫你決定什麼情境該選哪一條。
