第 2 章 · Part 1：概念與背景

claude-video 是什麼：架構與三大依賴

不是 MCP server，是一個 Agent Skill——三個現成工具組合出的巧妙管線。

⚠️
先破除一個常見誤解

網路上有些教學文章把 claude-video 誤植為 MCP Server，導致讀者白繞路去改 claude_desktop_config.json。claude-video 其實是一個 Agent Skill（/watch 指令），安裝與運作方式跟 MCP 完全不同，不需要碰任何 MCP 設定檔。

作者與專案定位

claude-video 由開發者 bradautomates 建立，GitHub 上短時間內就累積破萬星數（單日曾新增 400+ stars，被 fork 超過 1,100 次）。核心設計理念很清楚：不把自己當成一個 App，而是無縫嵌入 AI 工作流的「技能」——讓 AI 自己學會下載、轉錄、分析影片的整套流程，而不是要人類先看完影片再手動餵資料給 AI。

三大依賴

整套 pipeline 由單一主控腳本 watch.py 排程，背後靠三個現成、久經考驗的開源工具組合：

工具角色觸發時機
yt-dlp下載影片、優先抓取平台原生字幕每次執行的第一步
ffmpeg分離音軌、擷取關鍵影格無字幕需轉錄時分離音軌；一律用於抽取畫面
Whisper API語音轉文字（優先 Groq，OpenAI 備援）只有影片沒有任何字幕時才啟動

運作流程：把成本壓到極致的四步驟

claude-video 的架構可以說是把「省 token、省時間」追求到極致。整個 pipeline 依序執行：

  1. 先找免費字幕（零成本優先）——收到指令後第一步呼叫 yt-dlp，檢查影片平台有沒有提供字幕。命中的話，文字內容幾乎零成本取得，這是省錢的關鍵一步。
  2. 沒字幕才啟動轉錄 fallback——用 ffmpeg 把音軌分離出來，交給 Whisper API 轉錄，優先使用更便宜、更快的 Groq，OpenAI 當備援。
  3. 視覺處理：不暴力抽全部影格——只擷取「關鍵影格（keyframes）」，並內建一套去重演算法：把每張畫面縮成 16×16 的迷你灰階圖（縮小、去色是為了用極低運算成本快速估算兩張畫面像不像，不必逐像素比對原始解析度），只保留跟「前一張被選中的畫面」差異夠大的影格，過濾掉靜止或緩慢變化的冗餘畫面，讓 token 預算花在刀口上。
  4. 交付分析——把「帶時間戳的逐字稿」與「精選影格」一起交給 Claude，做到圖文並茂的理解，而不是只有乾巴巴的文字。
ℹ️
「交給 Claude」實際上是怎麼交的？

擷取出的關鍵影格會被編碼成圖片，跟逐字稿一起放進送給 Claude 的對話內容裡——用的正是 Claude 原生支援的圖片輸入能力（見上一章的澄清），不是什麼特殊管道。這也是為什麼影格數量要精挑細選：張數越多，佔用的上下文（context window）跟視覺 token 就越多，這正是第 8 章要談的成本問題的根源。

脆弱之處：依賴外部工具的代價

這套架構有一個明顯的風險：穩定性高度依賴 ffmpeg 與 yt-dlp 這兩個外部工具，只要其中之一更新或不相容，整個 skill 就可能無法運作。實測中也真的踩過這類問題（見第 5 章「常見問題排解」）：Windows 主控台的 cp950 編碼無法輸出字幕中的特殊字元、YouTube 字幕軌偶發 HTTP 429 限流——都是外部工具鏈天生的脆弱性，而不是 claude-video 本身的邏輯錯誤。

ℹ️
金鑰安全性也是已知取捨

claude-video 引導使用者把 API key 明文存放在 .env 設定檔，相較作業系統內建的金鑰管理服務安全性較低。個人使用沒什麼問題，但若要部署到企業環境，這點需要審慎評估。

小結

claude-video 沒有發明任何新技術，它的巧思全部在排序與取捨上——免費字幕優先於付費轉錄、關鍵影格優先於全影格，把三個現成工具組合成一條懂得省錢的管線。

理解了這套架構，下一章就能無痛安裝——因為安裝本身沒有任何魔法，就是把這條 pipeline 的可執行腳本放進 Claude Code 或 Codex 能找到的位置。
